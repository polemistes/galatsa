## 1. Context and summary

Galatsa must be extensible from the start, and every tool is an extension against the same interface: text, shapes, images, freehand drawing, tables, charts, maps and media, and also the importers, exporters and transitions. The editor has a quick mode with the basic functions and an advanced mode with everything. Every change a user makes must be undoable, one action at a time. The document model ([0001](0001-document-model-and-file-format.md)) already fixes how elements are stored (a fixed envelope, opaque `data`, open `ext` slots, references in `refs`, assets by hash) and how undo works (`DocumentUndoManager`, creation in two transactions, `group()` for several operations). The renderer ([0004](0004-rendering-engine.md)) draws extension elements through a drawing context it provides. Translations ([0003](0003-translations.md)) come from message bundles, one namespace per extension.

This document specifies the seven extension points (element type, tool, import, export, transition, command and panel), the command registry, how commands relate to undo, the editor services that commands and tools use, and how extensions are registered. The interface is TypeScript types plus a small runtime: the hosts that load extensions and the registry that runs commands. Every extension comes in two parts: a viewing part, which is all the player needs, and an editing part, which only the editor loads.

There are no third-party extensions. All extensions are first-party code bundled with the program at build time; nothing loads code from files or the network at run time, and there is no security model for foreign code. The interface does not prevent adding one later. The interface has no extension point for AI features, and none of the code here calls a language model, a suggestion engine or anything similar.

## 2. Ids, labels, modes and versions

**Extension ids** are lowercase words separated by dots (`galatsa.text`), the pattern of a message namespace (`NAMESPACE_PATTERN` in `@galatsa/i18n`). That makes the id usable in three places without escaping: as the first part of an element type id (`galatsa.text/text`, the grammar of [0001](0001-document-model-and-file-format.md) section 3.2), as the first part of every contribution id, and as the message namespace.

**Contribution ids** are `"<extension id>/<name>"`, with the name in the characters an element type name allows (`a-z 0-9 . _ -`, starting with a letter or digit). An extension names its contributions; the host prefixes them, so two extensions can never collide, and ids within one extension must be unique per kind. Ids are stable: documents store element type and transition ids, and user settings will store command and tool ids (shortcut overrides, toolbars).

**Labels** are message keys `"namespace:key"` (type `Label`). A definition never holds user-visible text, only keys, and the editor looks them up with its `I18n` when it shows them, so a change of language needs no reload. `messageKey(bundle, key)` builds a label whose key the type checker verifies against the bundle. A label's namespace is one of the extension's own, one of its dependencies', or `common`.

**Modes.** `Mode` is `"quick"` or `"advanced"`. Every contribution that users see has an optional `quick` flag; quick mode offers what has `quick: true`, advanced mode offers everything, so quick mode is a subset. The flag lives on the definition, next to what it marks, and is the single source for menus, toolbars, the keyboard map, the command search, the property panel and the import and export dialogs (`availableIn(quick, mode)`). Running a command checks the mode too, so a shortcut cannot reach an advanced command in quick mode.

**Shortcuts** are strings such as `"Mod+Shift+Z"`: modifiers (`Mod`, `Ctrl`, `Alt`, `Shift`, `Meta`; `Mod` is Ctrl on Windows and Linux, Cmd on macOS) and a `KeyboardEvent.key` value. `normalizeShortcut` gives the canonical spelling (modifiers in a fixed order, a single letter in lower case).

**Interface version.** `EXTENSION_API_VERSION` is `{ major, minor }`, now 1.4 (1.1 added named undo steps, section 4.2; 1.2 added `isEnabled` and `extensions` to the tool session and four resize cursors, section 5; 1.3 added the pointer in the camera's space, `ToolPointerEvent.local`, and offsets between spaces, `SceneQuery.offset`, sections 4.8 and 5; 1.4 added `applies` to fields, section 3.9). The minor version rises with every additive change (a new optional member, a new extension point); the major version rises with every incompatible one. An extension declares the version it was written against (`api`) and runs if the major versions are equal and its minor version is at most the host's.

## 3. Element types

An element type is what an extension tells the program about the elements it defines, in two parts. The **view** (`ElementTypeView<M>`, in the viewing entry) is what the renderer and the player need. The **editing part** (`ElementTypeEditing<M>`, in the editing entry, made with `defineElementEditing(view, ...)`) is what only the editor needs. `M` is the type's _model_: the data as the type understands it. Every method except `read` takes the model, never the raw data.

| Member          | Part    | Required | Purpose                                                                                       |
| --------------- | ------- | -------- | --------------------------------------------------------------------------------------------- |
| `name`, `label` | view    | yes      | Type id `"<extension id>/<name>"`; label for menus and the placeholder of an empty selection. |
| `typeVersion`   | view    | yes      | The newest layout of `data` this definition reads and writes (3.8).                           |
| `read`          | view    | yes      | Total reader from `data` to the model, with reports (3.2).                                    |
| `draw`          | view    | yes      | Draws the element in its local box (3.3).                                                     |
| `bounds`        | view    | no       | The area drawn when it reaches beyond the box (3.4).                                          |
| `hitTest`       | view    | no       | Whether a point hits the element (3.4).                                                       |
| `assets`        | view    | no       | Assets the element shows, so a viewer can load them ahead (3.6).                              |
| `name`          | editing | yes      | The name of the view it belongs to.                                                           |
| `upgrade`       | editing | no       | Writes for keys whose meaning changed between layouts (3.8).                                  |
| `references`    | editing | no       | Ids of elements and stops the data refers to (3.6).                                           |
| `textEditing`   | editing | no       | Where in-place text editing happens, for text-like types (3.5).                               |
| `capabilities`  | editing | no       | Whether the user may resize and rotate it (3.7).                                              |
| `properties`    | editing | no       | Adjustable values for the properties panel (3.9).                                             |

Methods that take the model are written as methods, not function properties, so TypeScript compares their parameters bivariantly and the hosts can hold definitions of different models in one list (`AnyElementView`, `AnyElementEditing`) without casts.

### 3.1 Where elements come from

Elements are created and changed only by commands (section 4). An element type defines no "create" method: its extension's commands build the initial data and call `insertElement`, which checks the data with the type's reader, writes it in the current layout and sets `refs` (3.6). Import builds elements into a fragment (6.1).

### 3.2 Data and validation

The document model keeps `data` opaque: the grammar reads its generic encoding (plain JSON and tagged shared types) and quarantines only what that encoding cannot hold ([0001](0001-document-model-and-file-format.md) section 2.1). What the data _means_ is the extension's, and the extension follows the same principle as the grammar, with one reading function:

- `read(data, typeVersion, report)` MUST be total: it never throws, whatever the data holds, because a peer, an older or newer version, or a damaged file may have written it. A value that does not fit is read as a default and reported (`report(path, problem)`). A missing optional key is read as its default without a report; every key a later layout added is optional (3.8). Reading the same data again reports the same things.
- Data is **valid** when reading it reports nothing. Before a command writes data, `insertElement` and `updateElementData` read the complete result with the type's reader and throw `InvalidDocumentError` with the reports if there are any, before anything is written. So a command can no more write data its own type would read differently than an operation can write what the grammar would change.
- **Lenient reading for growth.** A type MAY read a well-formed value that a later version of it could write (a choice it does not know, a number outside its own range) leniently: keep it in the data, draw a default or the nearest allowed value, and report nothing, so that adding an option or widening a range in a later version does not make older versions refuse every edit of the element. Such a value is then valid in the sense above, and the strictness moves to the type's own commands, which MUST check what they write against what this version allows. Two consequences: `updateElementData` and `insertElement` then accept such a value in the data (they check only what the reader reports), so a command that writes a value MUST check it itself; and `paste` (12.1), which checks a fragment's data with the same reader, pastes such values as they are, which is what keeps a later version's elements intact when they are copied through an older one. The shape type ([0010](0010-shapes.md), "Growing the format") reads this way.
- `read` is pure, so the renderer and the editor MAY cache the model until the element's data changes.
- The patterns of [0001](0001-document-model-and-file-format.md) section 3.4 apply: independent properties are separate keys, values that belong together are one JSON value, edited text is a `Y.Text`, concurrent collections are maps keyed by random ids with order keys, derived data is never stored, large binaries are assets, references are complete string values listed in `refs`.

A schema language (JSON Schema, a validation library) was considered and rejected (section 14): the reader has to produce a model with defaults anyway, and a schema would be a second definition of the same thing.

### 3.3 Drawing

Element types draw through a `DrawContext` that the renderer provides; they never reach the canvas. The context is defined without DOM types, so the renderer implements it over Canvas 2D, and the player, a thumbnail or picture export, or a test can implement it otherwise (`createRecordingDrawContext` records calls).

- **Coordinates.** `draw(model, ctx, box)` draws in the element's local, unrotated box: (0, 0) is the top-left corner and (`box.w`, `box.h`) the bottom-right, in world units. The renderer applies position, rotation, containers and the camera.
- **Precision.** Paths are renderer objects built like Canvas 2D paths (`moveTo`, `lineTo`, curves, `arc`, `ellipse`, `rect`, `roundRect`). The renderer converts every point itself, in float64 and relative to the camera, and clips geometry far outside the screen before it reaches the canvas ([0004](0004-rendering-engine.md), "Camera-relative drawing"), so element types never deal with precision at deep zoom. For the same reason the context offers only translation (`withOffset`), not scaling or rotation.
- **Primitives.** `fill(path, color)`, `stroke(path, style)`, `withOpacity(alpha, draw)`, `withClip(path, draw)`, `withOffset(x, y, draw)`. Colours are CSS colour strings.
- **Images** are drawn by asset id: `drawImage(asset, dest, { crop })`. The renderer picks the stored reduced level that matches the size on screen and never decodes the original unless it fills the view ([0004](0004-rendering-engine.md), "Image levels of detail"). It returns `"drawn"`, `"loading"` or `"missing"`, so the type can draw its own stand-in; the renderer redraws when a loading image arrives.
- **Text** is laid out by the renderer: `layoutText(content, style, width)` returns an opaque `TextLayout` with its size, and `drawText(layout, x, y)` draws it. Content is a plain string or rich text in its JSON form (a `Y.Text` delta). The renderer computes line breaks once at a reference size and scales them, and the editing overlay uses the same breaks, so text does not jump when editing starts ([0004](0004-rendering-engine.md), "One text layout"). Font families are generic names that the renderer maps to the fonts it bundles.
- **Text the element itself shows** (a "missing image" label) is looked up with `ctx.t(label, values)`.

### 3.4 Bounds, hit testing and level of detail

- `bounds(model, box)` returns the drawn area in the local box when it reaches beyond the box (a thick stroke, a shadow); the default is the box. The renderer uses it for culling and redraw regions.
- `hitTest(model, point, box, tolerance)` decides whether a point in the local box hits the element, within `tolerance` world units (the renderer converts its pixel tolerance). The renderer calls it only near the bounds; the default is the box grown by the tolerance. The shape sketch tests the real outline (an ellipse is not hit in its corners).
- **Level of detail.** `ctx.scale` is device pixels per world unit at the element, and `ctx.detail` is the renderer's request: `"full"`, `"reduced"` (small on screen or a fast camera; leave out fine detail) or `"box"` (a few device pixels; a filled box in the main colour is enough). Elements under half a device pixel are not drawn at all. A type MAY ignore the hint; the text sketch draws a bar at `"box"`, as [0004](0004-rendering-engine.md) asks for text under about 4 device pixels.

### 3.5 Text editing

A text-like type implements `textEditing(model, box)` in its editing part, returning the data key of its `Y.Text`, the text style, the text area in the local box, and whether the box height follows the text. The renderer's `beginTextEdit(id)` asks the type for this target, lays the browser's editing element over the area with the same style and line breaks, and binds it to the shared text.

**How typing forms undo steps.** Typing is not a command. The editor binding writes each keystroke in its own transaction with the binding's origin, which the document's undo manager tracks (`createUndoManager(doc, { origins: [binding] })`), so typing and commands share one undo history. The undo manager merges transactions of tracked origins that follow each other within its capture timeout into one step, so a burst of typing is one step. `group()`, which every command runs in, closes the open step when it starts and when it ends; so a command run during typing (bold, a style change) is a step of its own, and the typing before and after it are separate steps.

**Auto height.** With `autoHeight`, the box height follows the text. After a keystroke whose laid-out height differs from the box, the editor resizes the element right away, in the same event handling, with `resizeElement(..., { origin: binding })`: not through a command, so no `group()` closes the typing step, and the resize joins it. Undoing the typing takes the height back with it (tested).

**Formatting the selected text.** The editor's text service (4.8) gives the element and key being edited and the selected range. A formatting command (bold, italic, lists) reads it, formats the shared text in place inside `edit()`, and is one undo step. The text sketch's bold command does this, and is enabled only while text is selected in an editable text box.

### 3.6 References and assets

- `references(model)` (editing part) lists the ids of elements and stops the data refers to. Whenever a command writes data through `insertElement` or `updateElementData`, the host sets the envelope's `refs` to this list (`setRefs` writes only the difference), so copy, duplicate and paste remap the references ([0001](0001-document-model-and-file-format.md) section 3.5). A reference MUST be stored as a complete string value equal to the id.
- `assets(model)` (view) lists the assets the element shows. It is informational, for loading ahead and for notices such as "3 images are missing": the document finds asset references by scanning for asset ids, so nothing is lost if this list is incomplete.
- A command that writes an asset reference MUST register the asset's description with `addAsset` in the same command, also when the description is there already ([0001](0001-document-model-and-file-format.md) section 8.3). `addAsset` is untracked and is not undone with the command, which is intended: tidy up removes unused descriptions.
- Asset bytes are hashed and stored before the command runs (section 4.3), through the host's `AssetStore`.

### 3.7 When the extension is missing

The host resolves every element (`host.resolve(element)`) to one of: handled by its extension; handled by core (frames and groups); or a **placeholder**, because no loaded extension defines the type (`"missing"`) or the element's `typeVersion` is higher than the type's (`"newer"`). An element whose type throws while drawing is drawn as a placeholder too (`"failed"`), so one faulty extension never breaks a frame.

A placeholder is drawn by `drawPlaceholder`: the element's box, filled lightly and outlined with a dashed line one device pixel wide, with the localized reason and the type id ("Missing extension: examples.chart/chart") when there is room. The renderer and the player use the same function.

What the user may do is decided by `host.capabilities(element)`:

| Element                      | Move, stack, reparent, group, lock, delete, duplicate, paste | Resize                      | Rotate                     | Edit content |
| ---------------------------- | ------------------------------------------------------------ | --------------------------- | -------------------------- | ------------ |
| Known type                   | yes                                                          | unless the type forbids it  | unless the type forbids it | yes          |
| Placeholder (missing, newer) | yes                                                          | no                          | no                         | no           |
| Frame                        | yes                                                          | yes                         | no                         | yes          |
| Group                        | yes                                                          | yes, by scaling its members | no                         | no           |

Resizing a placeholder is refused because the extension may tie the box to the content ([0001](0001-document-model-and-file-format.md) section 9.5, decided with the users).

**Scaling groups and selections** keeps proportions: every element inside is scaled about the same point, through nested groups and frames (`planScale` and `applyScale`, one transaction). An element that may not be resized, such as a placeholder, is moved, not resized: it keeps its size and its centre lands where the scaled centre would. This follows from the decision that such elements are movable but not resizable.

Content edits are refused by `updateElementData` itself, so no command can edit the data of a placeholder by mistake. The placeholder's data and `ext` are never read, never upgraded and never written; a file round trip keeps them unchanged. Unloading an extension turns its elements into placeholders on the spot; loading it again brings them back.

A transition whose extension is missing plays as the route's default, and its stored value is kept. Missing tools, commands, importers, exporters and panels are simply not offered.

### 3.8 Layout versions and upgrades

The policy is that of [0001](0001-document-model-and-file-format.md) section 9.4, made concrete:

- `read` MUST read every `typeVersion` from 1 to its own. It is never called with a higher one: such elements are placeholders and are never down-migrated.
- Data is **never upgraded on load**. A live document may mix layout versions of one type.
- **Readers default missing keys.** Every key a later layout adds is optional, and its default MUST mean what older layouts implied (version 2 of the text sketch added `fontFamily` and `align`, defaulting to sans serif and left, which is how version 1 drew). So data of any older layout reads correctly in the newer one without being rewritten, and most upgrades write nothing but the new version.
- An element is upgraded **only when a user edits it**, just before the edit: `updateElementData` writes the type's `upgrade(data, from)` result, if it has one, and `setTypeVersion`, in one transaction of its own with origin `ORIGIN.upgrade`. That transaction counts as work but is **not undone**: an upgrade keeps the meaning of the data, so there is nothing to undo, and undoing the edit must not move the element back to an older layout that a peer's concurrent edit may already rely on. The edit itself is the command's undo step, as always. `setTypeVersion` never lowers a version.
- `upgrade` is for keys whose meaning changed. It SHOULD be avoided by design: a rewrite made by one user's upgrade can overwrite another user's concurrent edit of the same key. The first review found exactly that when the text sketch's upgrade wrote the old defaults explicitly: depending on which client won, one user's upgrade overwrote the other's alignment, and undoing the first user's edit set the layout version back. With defaults instead of writes, both edits survive in either client order and after the undo (tested).

### 3.9 Properties and fields

A `FieldDefinition<S>` describes one adjustable value: a key, a label, a control (`number` with range and step, `color`, `select` with labelled options, `toggle`, `text`), a `quick` flag, a getter, and the id of the command that changes it. When the user changes the value, the editor runs that command with a `FieldChange` (`{ ids, key, value }`), so every change is one undo step and goes through the same checks as any other command. For several selected elements the editor reads each and shows a mixed state when they differ. A field MAY say which elements it is for with `applies(model)` (since 1.4): one element type with several variants lists every field once, and the shape type ([0010](0010-shapes.md)) offers corner rounding only for kinds with corners and fill only for closed outlines. The editor shows a field for a selection only when it applies to every selected element; without `applies`, a field always applies.

An element type lists its fields in its editing part's `properties` (`S` is its model); the editor's properties panel shows them for the selection, filtered by mode (`host.properties(type, mode)`). This is how quick mode shows fewer adjustments than advanced mode on the same element: the shape sketch offers fill, outline and outline width in quick mode, and also the shape type, corner rounding and opacity in advanced mode. A value set in advanced mode stays in effect in quick mode; only its control is hidden (decided by the users).

**Continuous controls** (a slider, a colour being dragged, a number scrubbed with the mouse) use a gesture (4.7): while the user drags, the editor previews the value (`gesture.preview({ [id]: { data: { [key]: value } } })`) without changing the document, and on release runs the field's command once with the final value. So a slider drag is one undo step and one transaction, not one per pointer event.

## 4. Commands and the command registry

Every change a user makes to a document goes through a command: menus, toolbars, shortcuts, the property panel, tools, drag and drop, paste and import. A command (`CommandDefinition<A, R>`) has a name (id `"<extension id>/<name>"`), a label, an optional description, icon and shortcuts, a `quick` flag, `enabled` and `visible` predicates, an `undoable` flag, and `execute(ctx, args)`.

### 4.1 The context

The editor describes the document a command runs against in a `CommandEnvironment` for each call: the `Y.Doc`, its `DocumentUndoManager`, and the editor's services (4.8: selection, camera, mode, panels, scene queries, the text being edited, previews). The registry adds `extensions` (element types and capabilities), `mode`, `history` (undo and redo, 4.2) and `run(id, args)` for running another command as part of this one. The environment is passed to every call rather than held by the registry, so the registry has no hidden state about the editor, works the same for several open documents, and is easy to test (`createTestServices` gives services over a real document).

### 4.2 One command, one undo step

`registry.execute(id, env, args)`:

1. returns `{ ok: false, reason: "unknown" }` for an unregistered id, and `{ ok: false, reason: "disabled" }` if the command is not offered in the mode or `enabled` returns false (or throws);
2. otherwise runs `execute` inside `env.undo.group()`, which makes one undo step of everything the command does, whatever the capture timeout, and returns `{ ok: true, value }`;
3. a command run from inside another undoable command on the same document (through `ctx.run`, or `execute` while one is running) runs directly and joins the outer step. This matters: `group()` closes the open step when it starts, so a nested `group()` would split the outer command into two steps. The open step is tracked per undo manager, so commands on another document are never drawn into it;
4. a command with `undoable: false` runs without a step of its own. It is for commands that do not change the document themselves: the camera, panels, the mode, the selection, and undo and redo. If it runs commands that do change the document, each of those is one undo step, taken back if it fails, and its failure fails the outer command.

**History.** Undo and redo are commands like the others (in the built-in basics extension, section 12.1), with labels, shortcuts and quick-mode flags. They call `ctx.history.undo()` and `redo()`, which refuse (return false) while a gesture runs on the document or a command step is open on it, so an undo can never land in the middle of a drag or a command.

**Named steps.** Each step a command makes carries the command's id and its step label, so the editor can show "Undo move" ("Angre flytting"). A command may give `undoLabel`, a noun phrase for the step, because languages word the command and its step differently (the command "Flytt", the step "flytting"); without it, the step is named by `label`. The registry stores `{ command, label }` in the meta map of the Yjs stack item it made (a command that changed nothing tracked makes no item and renames none), and copies the meta when Yjs moves a step between the undo and redo stacks, which it does by making a new item. `history.undoStep()` and `redoStep()` give the step the next undo or redo would take (`null` if none; `{}` for a step no command made, such as typing). Yjs skips a step whose changes were all overwritten by others, so the step actually undone can then be an earlier one; the name is a label for a menu, not a promise. The step of a command run by another command has the outer command's name.

### 4.3 Rules for `execute`

- `execute` MUST be synchronous. `group()` spans a synchronous function, and an undo step that waited for a promise could swallow unrelated edits. Asynchronous work (reading a file, hashing an asset, decoding an image, an import) happens before the command runs, and its result is the command's argument.
- `execute` MUST change the document only through the operations of `@galatsa/core/ydoc` (and the helpers here that use them), with `edit()` for in-place edits of shared text and collections. It MUST NOT call `doc.transact`: the operations that create records (`addElement`, `group`, `addStop`, `addRoute`, `pasteFragment`, `importCopy`) refuse to run inside another transaction, because their first, untracked transaction must stay separate for undo to remove softly ([0001](0001-document-model-and-file-format.md) section 10); and a transaction with another origin would not be undoable or would not be recorded as work.
- Content edits use `updateElementData` (3.2, 3.8) and creation uses `insertElement`, so data is checked, upgraded and referenced the same way everywhere.
- Arguments SHOULD be plain JSON-compatible values, so that commands can be bound to shortcuts and menus and, later, recorded or scripted. `enabled` receives the arguments too, and SHOULD check them, because shortcuts and menus run commands without any.

### 4.4 A failing command leaves no trace

A command can fail midway: the operations check their arguments before writing, but a command of several operations may already have done some of them. If `execute` throws, the registry undoes the step the command had made and returns `{ ok: false, reason: "failed", error }`. The failed change does not cost the user their redo history: Yjs empties the redo stack when a new change is recorded, so the registry keeps a copy from before the command and puts it back after taking the change back (tested: redo still works after a failed command). Undoing a creation removes softly, as always. Inside a nested run, the error propagates to the outermost undoable command, which is taken back as a whole.

### 4.5 Quick mode

A command is offered in quick mode when `quick` is true. The registry lists commands per mode (`list(mode)`), builds the keyboard map per mode, and refuses to run a command that the current mode does not offer. Which commands are in quick mode is decided in each definition by the extension that owns it; the editor does not keep a second list.

### 4.6 Shortcuts

`registry.shortcuts(mode)` returns the keyboard map of a mode and the conflicts: when two commands offered in the mode claim the same shortcut, the first registered (in activation order) keeps it, and the conflict is reported so the editor can show it (`extensions:problem.shortcut-conflict`). A command not offered in a mode has no shortcut there; since advanced mode offers every command, two commands with the same shortcut always conflict there. User-defined shortcuts are a later addition on top of this map.

### 4.7 Gestures

A drag (moving, resizing, rotating, drawing) and a continuous control (3.9) must show their result live yet end as one undo step. `registry.beginGesture(env)` returns a `Gesture`:

- `preview(changes)` shows positions, sizes, rotations or data values for some elements (`PreviewChanges`, in each element's parent space) through the editor's preview service (4.8). **The document is not changed**: the renderer draws the preview instead of what the document says.
- `commit(command, args)` ends the gesture by running one command, as one undo step. A command that moves many elements batches its writes in `edit()`, so the drag is also one transaction: 50 elements dragged over 120 pointer moves give at most two document updates (the move and the work tracker's) and a few kilobytes, where writing on every move gave 12,000 updates and 164 kB.
- `cancel()` ends it and writes nothing. A cancelled drag is therefore not work on anything, and a delete that a peer made meanwhile still applies (tested).

Gestures are kept per document (per undo manager). One gesture runs per document; starting another cancels the first. Other commands may run during a gesture, on that document or another, and each is committed separately as its own step, which a later cancel of the gesture does not touch: the gesture has written nothing they could be entangled with. Undo and redo wait until the gesture ends (4.2).

Collaborators therefore see a drag when it ends, not while it happens. Showing other users' drags live can be added later as presence (an awareness channel), not as document changes.

### 4.8 Editor services

Selection, snapping, equal-size guides and text formatting must be writable as tools and commands against the interface, so the editor exposes its state through `EditorServices`, part of every `CommandEnvironment`:

| Service     | What it offers                                                                                                                                                                                                                                                                                                                                                                                                                       |

| `camera`    | The camera view; the visible part of the canvas in root space; set the camera (the editor anchors it in the innermost frame around its centre and keeps it within the zoom limits, [0009](0009-camera.md), so `get` after `set` may name another space for the same view); fit a rectangle.                                                                                                                                          |

## 5. Tools

A tool (`ToolDefinition`) is the canvas-interaction part of an extension: a name, a label, an icon, shortcuts that pick the tool, a `quick` flag, a toolbar group, a cursor, and `start(session)`, which returns a `ToolHandler` when the user picks the tool.

- **Input.** The handler receives pointer events (`pointerDown`, `pointerMove`, `pointerUp`, `pointerCancel`) with the position on screen, on the canvas in root space (`world`) and in the camera's own space (`local`: the frame the camera is anchored in, or the root), the pointer type, the button, the pressure and the modifiers, and key events (`keyDown`, `keyUp`, returning true when used). Events are plain objects without DOM types; the editor translates DOM events. A touch press may turn out to be the first finger of a pinch; the editor then cancels the tool's drag and takes back what the press did (the undo steps made since it, the selection and the current tool), so a tool may run commands on `pointerDown` ([0009](0009-camera.md)). `world` resolves a screen pixel wherever |world| × zoom stays within the precision budget of [0001](0001-document-model-and-file-format.md) section 7, which covers everything but deep zoom far from the root; there, `local` is exact, and `services.scene.offset` carries it into any container ([0009](0009-camera.md)).
- **Output is commands.** A tool never writes to the document. It runs commands through the session (`session.run`, one undo step each) or ends a gesture with one (`session.gesture()`, 4.7). The shape sketch draws its preview in the overlay and runs one insert command on release; the selection sketch previews a move through the gesture and commits one move command; the text sketch runs its insert command on click and asks the session to start text editing.
- **Overlay.** `drawOverlay(ctx)` draws previews (a rubber band, the outline of a shape being drawn) in root space above the document, with the same drawing context; the tool calls `session.requestOverlay()` when the preview changes. `ctx.scale` gives the size of a device pixel.
- **Session.** Besides running commands and starting gestures, the session gives the current environment (with the editor services, 4.8, for hit testing, rubber bands, snapping and selection), the zoom, cursor changes, `editText(id)` (the renderer's `beginTextEdit`), and `done()` to return to the default tool. Since 1.2 it also gives `isEnabled(command, args)`, whether `run` would accept a command now (the check a menu makes to grey out an entry), so a tool offers only what its commands would do; and `extensions`, the loaded element types and capabilities, so that a preview computed with `planScale` or `capabilitiesOf` (which take the document and the extensions, not a whole command context) shows what the command it ends in will do. Both were added for the selection tool ([0008](0008-selection.md)): without them a tool could not tell which handles an element gets without running the command, nor preview a scaling through groups.
- **Cursors.** The CSS cursors a tool may set; 1.2 added `nwse-resize`, `nesw-resize`, `ns-resize` and `ew-resize` for handles.
- **Modes.** Tools without `quick: true` are hidden in quick mode, with their shortcuts.

The selection tool, moving, resizing and rotating with handles are the built-in extension `galatsa.select` ([0008](0008-selection.md)), written against the same interface and running the basics' commands; snapping and guides come later. It asks `isEnabled` of those commands, which apply `capabilities` (3.7), to decide which handles an element gets.

## 6. Import and export

Importers and exporters share a `TransferContext`: a `Cancellation` (the host adapts an `AbortSignal` to it; `throwIfCancelled` and `CancelledError`) and `progress(fraction | undefined)`, where undefined means the amount of work is unknown. Both are asynchronous, so they can read and write large files without blocking, and both describe their file types (`FileType`: a label, media types and file name extensions) for file pickers, drag and drop and "save as".

### 6.1 Import

An `ImporterDefinition` has file types, an optional `sniff(head)` that recognises a file from its first bytes, and `read(source, context)`.

- **Whole or streaming.** The `ImportSource` gives the name, the media type and the size as the platform reports them, and both `bytes()` and `chunks()`, so each importer reads the file whole or as a stream, whichever suits it (an image needs all bytes; a long PDF can be read page by page).
- **Assets.** Images, video and fonts found in the file go into the host's `AssetStore` (`put` hashes the bytes and returns the asset id and description).
- **Result is content, not writes.** `read` returns an `ImportResult`: a fragment (the same structure copy and paste use, [0001](0001-document-model-and-file-format.md) section 3.5) and notices for the user (what was left out or approximated, as labels with values). The importer never touches the document. The editor pastes the fragment with one command (`pasteImport`, which uses `pasteFragment`), at the drop point or in the middle of the view, so the whole import is one undo step however large it is, and the document is resolved once rather than per element. `buildFragment` builds a fragment from new elements in their types' current layouts.
- **Choosing an importer.** `host.importersFor(file, mode)` lists the importers whose file types match the media type or name extension, in activation order; the editor uses `sniff` when that does not decide.

### 6.2 Export

An `ExporterDefinition` has one file type and `write(input, output, context)`.

- **Purged input.** The editor builds the input with `prepareExport(doc, assets, options)`: the document as a plain snapshot, **purged for sharing** (`purgeSnapshot`: removed content, revisions and delete marks gone, children of gone containers placed where the user sees them; [0001](0001-document-model-and-file-format.md) section 5.8), the route or selection to export, and an asset reader that serves only assets the purged document refers to. An exporter never sees the `Y.Doc`. So nothing that was deleted can leave the program through any export, whichever extension wrote it. (Saving the presentation itself is not an export; it is the file format's job. A shared `.galatsa` file is an export and is purged the same way.)
- **Output.** `output.write(chunk)` is called once for a whole file or many times for a stream; the host decides where the bytes go (a file, a download).
- **Pictures.** Exports made of pictures (PDF, a series of images, a video later) get `context.render`, which draws a region of the document (a rectangle in a container's space, like a stop's view) into an encoded image through the renderer and the element types, so the export looks like the canvas.
- **Result.** Notices, as for import.

## 7. Transitions and comfort

A stop's `transition` value ([0001](0001-document-model-and-file-format.md) section 6.1) is `{ "type": "<transition id>", "options": <JSON> }`, or null for the route's default; `readTransitionValue` reads it. A `TransitionDefinition<O>` has a label, a `quick` flag, `read(options)` (total, like an element type's) and `plan(request)`.

- **Request.** The start and goal as camera views in the same space (the player converts both to the space of their lowest common ancestor, so a flight between neighbouring stops deep inside frames stays precise), the options, the screen size and the comfort settings.
- **Motion.** `plan` returns a `CameraMotion`: a duration in milliseconds and `frame(time)`, which returns either a camera view or a cross-fade between two views with a mix from 0 to 1. At the end it shows the goal. The player calls `frame` on every animation frame; the motion is a pure function of time, so pausing and seeking need nothing from the transition. Breaking off a transition (the presenter chooses another stop, goes back or takes over the camera mid-flight) needs nothing from it either: the player calls `breakOff` (7.1), which works through `frame` alone.
- **Comfort.** Some viewers feel unwell when the camera moves and zooms. `ComfortSettings` carries `reducedMotion` (from the system's setting, the user's setting, or the presenter's toggle during a presentation), the largest zoom ratio, distance and duration (at normal speed) a transition should still fly (above them it should cross-fade), and a duration scale. `DEFAULT_COMFORT` holds calm defaults until the users set their own (7.1). Every transition gets the settings and MUST honour them.
- **The guard.** The player wraps every motion in `guardComfort(motion, from, to, comfort)`. With reduced motion, any frame that would show a view other than the start or the goal becomes a cross-fade from start to goal; so no transition, faulty or not, can move the camera against the viewer's setting. Without reduced motion the motion is returned unchanged.
- **No jumps when broken off.** No input during a transition may make the picture or its speed jump. When the player stops a running transition before its end, it MUST continue with `breakOff(running, time, comfort, next)` (7.1) rather than plan the next transition from the view on screen: that would stop a flight dead from full speed, and make a cross-fade jump to one of its views.
- **Comfort changed during a transition.** When the comfort settings change while a transition plays (the presenter's toggle, or the system's setting), the player MUST break the transition off with the new settings and the same goal, `breakOff(running, time, newComfort, next)`. With reduced motion switched on, the camera then stops where it is and the rest is a cross-fade from the view on screen to the goal: no frame after the switch shows a view other than the one on screen (or the two of a cross-fade in progress) and the goal. Wrapping the running motion in the guard again is not enough: its next frame would jump from the view on screen to a blend of the start and the goal.

### 7.1 The built-in transitions

`packages/extensions/transitions` (`@galatsa/extension-transitions`, extension id `galatsa.transitions`) has only a viewing part, so the player gets it without editing code (the viewer bundle test covers it). It offers three transitions, all in quick mode and without options: `fly` (the route default, `DEFAULT_TRANSITION`), `fade` and `cut`.

**The path.** The flight follows J. J. van Wijk and W. A. A. Nuij, ["Smooth and efficient zooming and panning"](https://vanwijk.win.tue.nl/zoompan.pdf) (2003; presented at IEEE InfoVis 2003, from memory: the PDF does not say). With u the position on the line between the two centres and w the width of the view in world units (here the screen width divided by the zoom), the paper measures motion by how fast the image seems to move, ds² = (ρ² du² + dw²/ρ²) / w² (its equation 6), and the flight is the shortest path in that metric. ρ trades zooming for panning. We use ρ = √2: the paper's 26 users chose 1.42 on average (standard deviation 0.47), and the authors suggest √2.

**Precision.** The paper's closed form (its equations 9) divides by the distance between the centres and subtracts nearly equal numbers when one view is much smaller than the other, so it fails for a pure zoom and loses all precision at the zoom ratios the model allows ([0001](0001-document-model-and-file-format.md) section 7). With x = ρ²u and y = w, the metric is the hyperbolic metric of the upper half plane divided by ρ (our derivation from equation 6; the paper notes that the paths are circles for ρ = 1 and ellipses otherwise), so `flight.ts` computes the same path as a hyperbolic geodesic: the length as 2 asinh(|P₁ − P₀| / (2√(y₀y₁))) / ρ, the point at a given length from its direction of departure without dividing by the distance, and the zoom factor as a sum of positive terms that keeps its relative precision down to 2⁻⁶⁴. The first half is computed from the start and the second from the goal, so each end keeps its own precision and the flight back is the same flight backwards. Inputs are scaled so that no square overflows. Everything is float64, in the space the player gives (the lowest common ancestor of the two stops, so a camera anchored in a frame flies in that frame's space), and every view keeps the start's `space`. Tested: the paper's equations to a relative 10⁻¹¹; a pure zoom, a pure pan, no motion; zoom ratios of 2⁶⁰ and from `MIN_ZOOM` to the precision limit a million units out, where consecutive views are exactly as far apart in the metric as the path lengths say (no jumps) and the deep end moves no faster on screen than the metric allows.

**Speed.** The paper moves at a constant speed V (s = Vt, its equation 3) and names acceleration at the start and deceleration at the end as further work. Our profile (our choice): a quarter of the time speeding up along a raised cosine, half at a steady speed, a quarter slowing down, so the acceleration is continuous and zero where the camera sets off and stops. The peak speed is 0.85 metric units per second (`FLIGHT_PEAK_SPEED`) and the mean 0.6375 (`FLIGHT_SPEED`). For comparison, the paper's users chose V = 0.90 on average (standard deviation 0.43) for a constant speed that felt "smooth, fluent, and suitable for a daily use application" on a notebook; even our peak is lower, because an audience did not choose it, an audience in front of a large screen has more of its field of view in motion, and some viewers get motion sickness (our choice; the users' requirement is to counter motion sickness). By equation 6, a metric speed of 0.85 per second means at most 0.85/ρ = 0.60 screen widths per second of panning, or a zoom by e^(0.85ρ) = 3.3 times per second (1.7 doublings), or a mix within the ellipse ρ²u̇² + ẇ²/ρ² ≤ (0.85 w)². A flight lasts its length at that speed, but at least 500 ms so a small move is not abrupt, times `durationScale` (our choices).

**Limits.** `DEFAULT_COMFORT` has `maxFlightZoomRatio` 32, `maxFlightDistance` 3 screen widths and `maxFlightDuration` 4,200 ms at normal speed (previously 64, 4 and 4,000 ms, at a peak speed of 1.0). At the default speed a pure zoom by 32 takes 3.84 s and a pan of three widths 4.03 s, so all three limits mark about four seconds of flight; the duration limit is a little above the other two so that it does not cut a pure pan or zoom short, and catches combinations within them (a zoom by 4 to a place two widths away would take 4.7 s). It is measured before `durationScale`, so slowing down does not turn flights into cross-fades. Above any limit, between views in different spaces, and with reduced motion, `fly` cross-fades: 700 ms times `durationScale`, with the opacity on a raised cosine. A limit that is not a number (NaN, or missing from an older or damaged settings object) counts as exceeded, so it gives a cross-fade rather than letting any flight through. A view with a zero, negative or non-finite zoom or centre gives a cut: to the goal, or, when the goal is the view that is not usable and the start is usable, the camera stays at the start, so the renderer never gets NaN (all three transitions). The numbers are our choices, not taken from a study, and have not been tried on viewers; the users can change them.

**Settings.** `ComfortPreferences` is what the user stores: `motion` (`"system"`, `"reduce"` or `"allow"`) and the four numbers. `readComfortPreferences` reads them totally and keeps the numbers within bounds (zoom ratio 1 to 2⁶⁴, distance 0 to 10⁶ widths, duration 0 to 60 s, duration scale 0.25 to 4). `resolveComfort(preferences, system, presenter)` gives the `ComfortSettings`: the presenter's toggle during a presentation wins, then the user's preference, then the system's setting. `watchSystemReducedMotion(matchMedia, onChange)` follows the system's setting through the media query `(prefers-reduced-motion: reduce)` ([Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#prefers-reduced-motion), a W3C Working Draft: the user prefers an interface that removes or replaces motion-based animation that causes discomfort for people with vestibular motion sensitivity or distraction for people with attention deficits); it takes the function as an argument so the package stays free of DOM types. [WCAG 2.2, success criterion 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) (level AAA) asks that motion animation triggered by interaction can be disabled, and names dizziness, nausea and headaches as reactions. `COMFORT_LABELS` has the labels for a settings view, in Norwegian and English.

**Breaking off.** `breakOff(running, time, comfort, next?)` (in `break-off.ts`) takes the running motion as the player plays it (guarded), the time since it started, the comfort settings, and optionally the next transition (`{ transition, options, to, viewport }`), and returns the motion to play from then on, from its time 0. It needs nothing from the transitions, so any transition can be broken off, and its result can be broken off again (the presenter presses "next" several times):

- On a flight, the camera goes on along its path while a time warp slows it down: the rate of the flight's own clock falls from 1 to 0 along a raised cosine, so the speed and the acceleration are continuous where it is broken off, and the camera comes to rest within `BRAKE_DURATION` (600 ms) times `durationScale`, sooner near the end so it never passes the goal (our choices). From the peak speed that brakes about as hard as the end of a flight of a little over two seconds.
- On a cross-fade, the mix goes on, or turns back, between the two views on screen until one of them fills the screen: the next goal if it is one of the two (going back turns the fade around), otherwise the one that dominates once the fade has slowed down. Heading for that end already, the mix follows a cubic from its current value and rate to the end at rest, short enough that it never passes the end; heading away, it slows down within a quarter of a cross-fade and then goes back from rest. No other view is shown.
- Then `next` is planned from the view it came to rest at, with the given comfort settings, and guarded with `guardComfort` inside `breakOff`, so the player does not guard the result again. Without `next`, the motion ends at rest, for the presenter to take over the camera.
- With reduced motion, a flight is not slowed down along its path (that would show other views): it stops where it is, and the next transition (a cross-fade under reduced motion) starts from the view on screen. A cross-fade in progress goes on between its own two views as above. So after reduced motion is switched on, no frame shows a view other than what was on screen and the goal.

`restingView(frame)`, the view on screen or the dominant view of a cross-fade, is kept for a player that only needs to know where the camera is; continuing from it directly gives the jumps above.

## 8. Panels

A `PanelDefinition` adds user interface to the editor: a name, a label, an icon, a `quick` flag, a location (`side`, `bottom` or `floating`), a `visible` predicate, and its content. The interface does not depend on any user interface library; there are two kinds of content:

- **Fields** (`{ kind: "fields", fields }`): a list of field definitions (3.9) whose values are read from the editor context and whose changes run commands. Most panels (document settings, defaults, options of a tool) need nothing more, and the editor draws them in its own style, in both languages, accessible by keyboard, without the extension writing any user interface code. The text sketch's "Text defaults" panel is one.
- **Custom views** (`{ kind: "custom", binding, view }`): for panels that need their own interface (a map editor, a chart data table). `CustomPanelViews` is an empty interface that a user interface binding fills by declaration merging (tested); the editor's interface is Svelte (the users' choice), and its binding ([0007](0007-editor-foundation.md)) adds `svelte?: Component<PanelProps>`, with `PanelProps` giving the panel the command context. Until a binding does, a custom panel cannot even be written, so the interface package never refers to a UI library, and the player, which has none, never sees such panels. Only the Svelte binding is built; a binding for other libraries is not planned.

Panels use the extension's message namespace for their text, like every other contribution.

**Overlays.** Besides panels, an editing part may contribute overlays (`overlays`, `OverlayDefinition`): drawings in root space over the canvas outside any tool, per mode and while `visible`, such as the line of a route ([0013](0013-routes-and-stops.md)). Additive; it needs the next minor version.

## 9. Registration and lifecycle

### 9.1 The manifest

An extension has two parts, in separate modules:

- The **viewing part** (`ViewExtension`): an id, its own version (shown to users), the interface version it was written against (`api`), its dependencies, its message bundles, its element type views and transitions, and optional `activate` and `deactivate` hooks. It MUST NOT import editing code (commands, tools, the editing entry at run time, the document's Yjs operations), so a viewer that loads it carries none of that (section 10).
- The **editing part** (`EditExtension`): the viewing part it belongs to, extra dependencies and bundles that only editing needs, its contributions (`elementTypes` editing parts by the views' names, `tools`, `commands`, `importers`, `exporters`, `panels`), and its own optional hooks.

The player loads viewing parts into a `ViewHost`; the editor loads editing parts (each with its viewing part, checked, activated and unloaded as one extension) into an `EditorHost`, which also accepts a viewing part alone.

Contributions are **declared**, not registered from code. So the host can check everything before activating anything, the editor can list commands and tools without running extension code, and a failing activation leaves nothing half-registered. `activate(context)` is for what needs code: preparing a cache, or checking whether an optional dependency is active. It is synchronous; an extension that needs to load data does so lazily, when first used, so starting the program never waits for an extension. `deactivate` releases what `activate` acquired.

### 9.2 Message namespaces

An extension's bundles are registered with the program's `I18n` when it is activated. Each bundle's namespace MUST be the extension's id or a whole-word prefix of it (`galatsa.shapes` for `galatsa.shapes.arrows`), so that several extensions shipped together can share one bundle, as the three sketches share `examples`. When several extensions share a namespace it stays registered until the last of them is unloaded. At load time the host checks every label in every contribution: its namespace must be the extension's own, a dependency's (the dependency's id or a whole-word prefix of it), or `common`, and a key in one of the extension's own bundles must exist. A typo in a label is therefore a load problem, not a missing text at run time.

### 9.3 Versions

An extension runs if its `api` major version equals the host's and its minor version is at most the host's (`isApiCompatible`). Dependencies name ids without version ranges, because all extensions are built and shipped together and cannot be out of step; ranges would only matter for third-party extensions, which are not planned.

### 9.4 Order and problems

`host.load(extensions)` checks each manifest (id, names, labels, namespaces, layout versions, editing parts without a view, field keys, interface version, duplicate ids), then activates the extensions one at a time: always the first, in the given order, whose dependencies are settled. So the order changes only where a dependency requires it, and activation order (which decides shortcut conflicts) is deterministic. A required dependency must be active (from this load or an earlier one); an optional dependency that is being loaded is activated first, and one that is absent or fails is no problem. Extensions that use each other only optionally are activated in the given order, not refused as a cycle.

One extension's failure never stops the others. It is reported as a `LoadProblem` with a code and left out, together with every extension that requires it:

| Code                 | Meaning                                                          |
| -------------------- | ---------------------------------------------------------------- |
| `invalid`            | The manifest fails a check; `detail` says which.                 |
| `duplicate`          | An extension with this id is loaded already.                     |
| `api-version`        | Written for an interface version this host does not implement.   |
| `missing-dependency` | A required dependency is not there.                              |
| `dependency-failed`  | A required dependency was left out.                              |
| `cycle`              | Its required dependencies form a cycle.                          |
| `activate-failed`    | `activate` threw; its messages and contributions are taken back. |

`problemMessage(problem)` gives a user-facing message for each (`extensions:problem.*`, in both languages); `detail` is English for developers. The program goes on without the extension: documents that use it show placeholders (3.7).

### 9.5 Unloading

`host.unload(id)` unloads the extension and, first, every active extension that requires it (those that use it only optionally stay), in reverse activation order: their contributions are removed, their message namespaces unregistered (unless still shared), and `deactivate` is called. Elements of their types become placeholders, with their data untouched. Development hot reload replaces an extension by unloading and loading it.

## 10. Where the code lives, and dependencies

The interface is a new package, `packages/extension-api`, and not part of `@galatsa/core`:

- Core is the document model, used by the file format, the player and later the sync server. The extension interface brings in translations (labels, bundles), input events, panels and file import and export, none of which the document model needs, and a dependency on `@galatsa/i18n` would make every file of core subject to the hard-coded text check.
- Like core, the package is environment-agnostic: no DOM or Node types. The drawing context, input events, editor services and file sources are described in plain types that the renderer and the editor adapt.

It has two entries, matching the two parts of an extension:

- `@galatsa/extension-api`: the viewing part (ids, labels, the drawing context, element type views, transitions and the comfort guard, placeholders, `ViewExtension`, `ViewHost`). Nothing reachable from it needs Yjs or the document's operations at run time.
- `@galatsa/extension-api/editing`: everything in the viewing entry plus the editing part (element type editing, fields, panels, tools, commands and the registry, gestures, editor services, import and export, `EditExtension`, `EditorHost`, and the helpers that write documents: `insertElement`, `updateElementData`, `planScale`, `applyScale`, `buildFragment`, `pasteImport`, `prepareExport`).

The examples follow the same split: `@galatsa/extension-examples/view` has only their viewing parts. A test (`scripts/lib/viewer-bundle.test.ts`) bundles what a player imports (the viewing host, the comfort guard, the placeholder, the built-in transitions with their comfort settings, and the examples' viewing parts) with Vite and the workspace settings, and fails if the bundle contains Yjs's undo manager, the document's operations or the command registry, or grows past 80 kB; on 2026-11-27 it was 31 kB unminified without the transitions and 46 kB with them, against 409 kB for the editing entry with the same extensions. The first review measured 403 kB for the earlier single manifest, because a manifest that lists commands pulls in everything they import.

The package depends on `@galatsa/core`, `@galatsa/i18n` and `yjs` (13.6.33, already a dependency of core; used for types and, in the editing entry, to reach shared text). No new third-party package is added.

`packages/extensions/examples` (`@galatsa/extension-examples`) holds the sketches of section 11. It is a library in the extensions folder like the real extensions will be, with its own message folder, so the translation check covers its text.

`packages/extensions/basics` (`@galatsa/extension-basics`) is the first real extension: the commands every element has (12.1). It depends on `@galatsa/core`, `@galatsa/extension-api`, `@galatsa/i18n` and `yjs`; its test helpers (`@galatsa/extension-basics/testing`, not part of the program) also use the shape sketch. No new third-party package.

Core gained one operation, `setTypeVersion`, and one transaction origin, `ORIGIN.upgrade` (3.8), because the envelope had no way to raise an element's layout version after creation. With the basic commands, its undo manager learned to finish an undo or redo before the work tracker judges it (filling holes first, holding back a change of container that would take an element out of another user's delete, and doing one that would move something on the canvas with a rebase that keeps its place; what it writes joins the step), [0001](0001-document-model-and-file-format.md) section 10.

## 12. What the editor, the renderer and the player provide

The interface fixes what each side gives the other. The other side of each contract is built with the editor, the renderer and the player:

- **Renderer:** a `DrawContext` over Canvas 2D (camera-relative float64 paths, clipping, image levels, text layout with one layout for drawing and editing, `ctx.t`), calling `host.drawElement` for each visible extension element and drawing frames and groups itself; `bounds` for culling and `hitTest` for picking; `beginTextEdit` driven by `textEditing`; a `RegionRenderer` for exports.
- **Editor:** a `CommandEnvironment` per call, with the editor services (4.8) and a preview drawn by the renderer; menus, toolbars, the keyboard map, the command search and the properties panel built from the registry and the host per mode; a `ToolSession` with gestures; translating DOM input to tool events; the import flow (choosing an importer, an `AssetStore`, progress and cancel, pasting with one command) and the export flow (`prepareExport`, output to a file); a field renderer for panels and properties, and the Svelte binding for custom panels; the selection tool and the buttons and keys that run the basic commands (12.1); the system clipboard, carrying the fragments that "copy" returns and "paste" takes; showing load problems and shortcut conflicts.
- **Player:** a `ViewHost` with the viewing parts' element types and transitions, `drawPlaceholder`, and `guardComfort` around every transition, with comfort settings from the system and the presenter (`resolveComfort` and `watchSystemReducedMotion`, 7.1), `DEFAULT_TRANSITION` for stops that name none, and `breakOff` (7.1) whenever a transition is stopped before its end: another stop, going back, taking over the camera, and a change of the comfort settings during the transition (with the new settings and the same goal).

Rules common to all of them:

- **What may be acted on.** An element the user sees (not deleted, dissolved or tidied away); not locked, and not inside a locked container the user sees (0001 section 5.6), except for `copy` and `duplicate`, which do not change it (copies are not put into a locked container), and `unlock`; scaling also refuses when a member of a scaled group or frame is locked, while deleting a group or frame deletes its locked members (decided by the users); and allowed by `host.capabilities` (3.7): resizing and rotating are refused for placeholders and for types whose `capabilities` forbid them, rotating for frames and groups. Elements of a missing extension can be moved, scaled with others (moved, not resized), restacked, reparented, grouped, locked, deleted, duplicated, copied and pasted, with their data untouched.
- **All or nothing.** If one of the elements may not be acted on, the command is refused as a whole, so a menu entry is greyed out rather than doing part of the job. `enabled` checks the arguments (shortcuts and menus run commands without them, 4.3), and `execute` checks them again and throws, so it can never write past the check.
- **One step, few transactions.** Every command is one undo step, through the registry's `group()` (4.2): the registry wraps every undoable command, so [0001](0001-document-model-and-file-format.md) section 13.21 is settled there, and the tests check that grouping, duplicating and pasting, each several transactions, are one step. Commands that only change values write them in one `edit()` transaction (move, resize, rotate, lock, unlock), so a drag committed as one of them is one document update. Commands that create records (group, duplicate, paste) cannot be one transaction (0001 section 10), and restacking and reparenting are one transaction per element, because an operation that re-keys a list (0001 section 4.1) must not run inside another transaction.
- **Fragments from the clipboard are checked.** `paste` reads its fragment with `readFragment`: every element, stop, route, asset description and fallback view must read cleanly with the document's grammar, the roots must be top-level elements of the fragment, and every other element must lie inside a root in the effective tree, that is with a frame or group of the fragment as each parent on the way up (any other parent counts as the root, 0001 section 5.1, and an element outside every root would be pasted without the delete mark that lets undo remove it), with its position written in the space of an element of the fragment (copy writes its container's; any other space would leave the pasted record naming an unrelated element of the document). The data of elements whose type is loaded must read cleanly with the type's reader (3.2), and the data of frames and groups with core's layout (a frame's `clip`, `fill` and `stroke`, nothing else; a group has no data); elements of a missing extension or a newer layout are pasted as they are.
- **Modes and shortcuts** (Claude's choice, to be revisited with the editor): quick mode offers move, resize, scale, rotate, reparent, bring to front, send to back, group, ungroup, delete, duplicate, copy, paste, undo, redo and select all; one step forward or back, lock and unlock are in advanced mode. Shortcuts: `Mod+Z` undo; `Mod+Shift+Z` and `Mod+Y` redo; `Mod+A`, `Mod+C`, `Mod+V`, `Mod+D`; `Mod+G` and `Mod+Shift+G`; `Mod+Shift+L` lock; `Delete` and `Backspace`; `Mod+]`, `Mod+[`, with Shift to the front or back (see 13, "Can wait" 1, for keyboards that need AltGr for brackets).

**The undo test** (`undo.test.ts`). A seeded random sequence of a thousand commands through the registry (the commands above, insertions of shapes, frames, elements of a missing extension and a type that may be neither resized nor rotated, undo and redo, with valid arguments and arguments that are refused) is undone step by step until nothing is left to undo, which must give the empty document, then redone the same number of steps, which must give the state after the thousand commands; twice. Every undo and redo, during the thousand commands and after, must give exactly the state the step it takes back started from, or the one the step it makes again ended in. The random commands include pasting an older fragment again, moving into a container at a stacking index, locking containers, grouping everything in a container and moving a container into its own descendant. States are compared as the user sees them: `purgeSnapshot(toSnapshot(doc))`, the document as exported for sharing (positions resolved, no revisions, delete marks or removed records), because undo leaves removed records and new revisions behind by design. Along the way, a refused command writes nothing and a command makes at most one step. Ids, order keys and writer keys come from seeded sources, so a seed reproduces a run exactly. Checking every step takes a snapshot per step, some two minutes per seed: seeds 1 to 42 passed with every step checked when this was written; by default three seeds run with the two ends checked, and one seed with every step checked over 250 commands (`UNDO_SEEDS`, `UNDO_STEP_SEEDS` and `UNDO_STEP_COMMANDS` in the environment change that). One user alone never needs an undo finished: the test checks that no hole is filled and no change of container is held back or rebased. So does `alone-after-concurrent.test.ts`, for one user working alone on a document two users edited concurrently before (positions converted from other spaces, broken cycles, survivors of deletes).

**Undo with two users** (`concurrent.test.ts`). Two replicas run random commands, undo and redo among them, and sync at random moments; then each undoes everything, syncing after every step. Every undo and redo is checked against what "each user undoes only their own changes, and none of the other user's changes is lost" means under the rules of [0001](0001-document-model-and-file-format.md) sections 5 and 10:

1. **Values and places.** No value the other user wrote that is current when the undo starts is replaced or removed by it: envelope keys (position, size, rotation, order key, container, rebase, lock, name, dissolved flag, layout version), data and ext keys, and the entries and items of shared types inside them. Checked on the Yjs items: each is still there, holding its value, after the undo. And nothing moves on the canvas except by positions the undo writes: with every position the undo changed put back, every element the user saw is where it was before (checked on the resolved document, independently of how the code finds what an element's place depends on; elements whose position is converted from another space by rule 3, which happens only after conflicting concurrent changes of container, are left out, because such a position can shift with any change of container along the way, 0001 section 13, 16). So an undo never takes back, in effect, a move the other user made, such as moving the group the user is ungrouping by undo.
2. **Deletes.** Nothing the other user's delete hides comes back.
3. **What disappears.** An element the user saw that is gone after the undo is gone through a delete mark or a dissolve this user wrote (the undo of their own creation or grouping, the redo of their own delete or ungrouping). Such a removal hides only what the user saw, keeps what the other user did without knowing of it, and can be taken back (0001 section 5.5), so it is not a loss.
4. **The undo is done.** Every plain value the step wrote in an element's envelope or data that is still there when the undo starts is taken back: afterwards the key holds the value from before the step, or at least no longer the step's value (a change of container done with a rebase that keeps the place). Only what rule 2 holds back is exempt. Without this rule, an undo manager that held back every change of container passed the other three.

After every sync, both replicas hold the same document. Four seeds of 400 steps run by default (`CONCURRENT_SEEDS` and `CONCURRENT_STEPS` in the environment change that); seeds 1 to 40 with 600 steps passed when it was written. Rules 1, 2 and 4 hold because the undo manager finishes every undo and redo before the work tracker judges it ([0001](0001-document-model-and-file-format.md) section 10): it fills holes first, holds back a change of container that would take an element out of a delete, and does one that would move something on the canvas with a rebase that keeps its place. Before that, the test found an element deleted with its frame coming back when the other user undid moving it in or undid a grouping, a hole that let the tracker keep such an element for good, and an undone grouping taking back the other user's move of the group.

## 13. Open questions and known limitations

**Answered by the users** (2026-11-27):

1. The program decides which functions are in quick mode; users cannot move functions between the modes (not now). The `quick` flag on each definition is the only source.
2. Settings made in advanced mode stay in effect in quick mode; only their controls are hidden there.

**Can wait** (to be settled where noted, or when they matter):

1. Shortcut matching on keyboard layouts where a key needs AltGr or Option (`Mod+[` on a Norwegian keyboard) and on macOS; and treating `Mod` and `Ctrl` as the same key on Windows and Linux when looking for conflicts. Matching is settled in the editor foundation ([0007](0007-editor-foundation.md), "The keyboard map"): AltGr is not a modifier of a shortcut, punctuation and digits also match by their place on a US keyboard, letters by character, and `Ctrl` is `Mod` on Windows and Linux. Conflict checking across layouts, and whether the chosen shortcuts suit a Norwegian keyboard and macOS, remain for the editor shell's shortcut handling.
2. Optional dependencies: an extension that uses an unloaded one optionally is not told; it checks `isActive` when it needs it.
3. Label keys in a dependency's or the common namespace are not checked at load time (only the namespace is).
4. `buildFragment` makes only top-level elements with generated ids, so an importer cannot yet build frames, routes or references between the elements it imports; it can build the `Fragment` structure itself until a richer builder is needed.
5. `refs` follows `references` only for writes through `updateElementData` and `insertElement`; a command that edits shared data in place with `edit()` must call `setRefs` itself.
6. The hosts send no change events (an extension loaded or unloaded while a tool or panel of it is open); the editor reloads extensions only at start and in development for now.
7. Settled in 1.1: undo steps are named after their command (4.2).
8. `guardComfort` catches a transition that throws only with reduced motion; without it, a throwing transition's error reaches the player.
9. The interface version check (same major, minor at most the host's) could be simplified to one number while all extensions ship together.
10. The basic commands resolve the document anew, several times per call, and `copy` and `duplicate` convert the whole document to its JSON form to cut out a fragment. That is fast enough for the documents of phase 1 (a thousand commands on documents that grow to some 700 element records take a few seconds in the tests, test overhead included), and should use the incrementally updated resolver once core has one.
11. `duplicate` offsets its copies by 16 screen pixels at the camera's zoom when the editor passes no offset (Claude's choice of distance).
12. The z-order commands treat an element inside a gone container by the slot of that container, as the core operations do; restacking several elements in one gone container at once can leave some of them in it. Rare (it needs a selection inside a dissolved group whose members are still shown), and nothing is lost.

**Known limitations:**

1. No third-party extensions: no loading of code at run time, no sandbox, no permissions. Adding them later needs a security model, and probably running foreign extensions in a worker, which this interface does not prevent (draw calls and commands are plain data and calls).
2. Commands are synchronous (4.3). A long operation that has to write a lot (an import of thousands of elements) builds a fragment first and pastes it with one command on the main thread. Pasting resolves the document once instead of once per element, which [0001](0001-document-model-and-file-format.md) section 11 recommends for bulk creation; how long a very large paste takes has not been measured.
3. Collaborators see a drag when it is committed, not while it happens (4.7).
4. The drawing context has no gradients, shadows, blend modes or patterns yet. Adding them is additive (a minor version), when an extension needs them.
5. `updateElementData` reads the element's data from the document for every edit. That is cheap for the planned types; a table with thousands of cells should edit its shared maps in place with `edit()` and check only what it writes.
6. Field controls are a small fixed set. New controls are additive.
7. A broken-off flight comes to rest, smoothly, before the next one sets off from rest, instead of carrying its speed into the next flight: the optimal path from a view leaves in its own direction, and a path that starts with a given velocity would not be the optimal one. A cross-fade broken off towards a third view first settles on one of its two views, which is then seen alone for a moment before fading to the third. With reduced motion switched on mid-flight, the camera stops at once: a change of speed, not of the view, which is what the setting asks for.
8. The flight measures views by the screen width (as the paper does), also on a portrait screen, where the height is the larger side.
9. **Stacking after an undone change of container.** Undoing a grouping after another user brought the group to front keeps the members where that user's move put them on the canvas, but puts them back in their old places in the stacking order, behind what the group had been brought in front of, where an ungrouping would leave them in front ([0001](0001-document-model-and-file-format.md) section 13, 23).
10. **An undo or redo that changes a container is slower.** Finishing it takes one pass over all elements with two resolutions of the document: 55 to 105 ms with 5000 elements in 50 frames, against under 1 ms for undoing a move (0001 section 13, 24).

## 14. Rejected alternatives

- **The interface in `@galatsa/core`.** It would make core depend on translations and carry user interface concepts the player and the server do not need (section 10).
- **Registering contributions from `activate` code** (as in some editors' extension systems). It allows lazy activation, which bundled first-party extensions do not need, and loses the check of the whole manifest before anything runs.
- **A schema language for element data** (JSON Schema or a validation library). The reader must produce a model with defaults anyway; a schema would be a second, possibly inconsistent, definition of the same data, and an extra dependency.
- **Migrating element data on load.** Rejected in [0001](0001-document-model-and-file-format.md) section 9.4: it would rewrite every element on every replica and lose merge identity; upgrades happen with edits instead.
- **Asynchronous commands.** An undo step that waits would capture whatever else happens meanwhile; doing the asynchronous part first and passing its result keeps one command one step.
- **Tools that write directly to the document.** Undo would then depend on each tool grouping its own writes correctly; with commands and gestures, the registry does it once.
- **Gestures that write on every pointer move** (the first version). Each move wrote every element in its own transaction, a cancelled drag counted as work on the elements (so a peer's concurrent delete no longer applied), and one drag of 50 elements made 12,000 document updates and grew the document by 164 kB. Previewing and committing once has none of these costs.
- **One manifest for viewing and editing.** Simpler, but a manifest that lists commands imports their code, so the player would carry Yjs and the editing code (403 kB measured).
- **Giving exporters the live document.** Each exporter would have to remember to purge, and one that forgot would leak deleted content. The host purges once, for all.
- **UI library components in panel definitions** (Svelte components directly in `PanelDefinition`). The interface package would depend on the library, and the player and tests would carry it.
- **Version ranges for dependencies.** All extensions ship together; ranges add checks that can never fail.
