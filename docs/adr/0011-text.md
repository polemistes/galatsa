# 0011 Text

- Status: proposed
- Date: 2026-11-27
- Code: `packages/extensions/text` (`@galatsa/extension-text`, and `@galatsa/extension-text/view` for the viewing part); in `packages/renderer`: `rich-text.ts`, `text.ts`, `text-dom.ts`, `text-edit.ts`, `fonts.ts`, `fonts.css`, `beginTextEdit` in `renderer.ts`, `drawText` in `draw-context.ts`, `textRendering` in `canvas.ts`; in `packages/editor`: `text-edit.ts` and the hooks for it in `editor.ts` and `services.ts`; `FONT_PACKAGES` in `scripts/lib/licenses.ts`; `tests/e2e/text-edit.spec.ts`, `tests/e2e/text-visual.spec.ts`

## Context

[0004](0004-rendering-engine.md) chose to draw the canvas ourselves and to edit text with a browser element laid over it, and asked for one text layout for drawing and editing (line breaks computed once at a reference size and scaled), bundled fonts waited for before layout, and text that does not jump when editing starts. It named the largest risk of owning text, rich text and line breaking, and suggested trying first to let the browser lay the text out in a hidden element and read the lines back. [0005](0005-extension-interface.md) gave the interface: `layoutText` and `drawText` on the drawing context, `textEditing` on a type's editing part, the editor's text service, typing as part of the undo history, and the auto height. The text sketch (`examples.text`) used all of it except in-place editing, which did not exist.

This is the real text: the extension, the layout, the fonts and in-place editing.

## Decision

| Topic      | Decision                                                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Layout     | The browser lays text out in a hidden element at 1,000 pixels; lines, baselines and where each run starts are read back. The canvas draws those positions.               |
| Editing    | The same element, scaled onto the screen with a CSS transform, made editable. It never holds the text: every edit goes to the shared text and is shown from there.       |
| Same look  | Measured in Chromium and Firefox at zoom 0.1, 1, 8 and 40: the edited and the drawn text agree to a pixel of rasterising, and the text does not move.                    |
| Fonts      | Noto Sans, Noto Serif and Noto Sans Mono (SIL Open Font License 1.1), from the Fontsource packages, shipped with the program; layout waits for them.                     |
| Data       | One element type, `galatsa.text/text`, layout version 1: shared rich text and four style keys (font, size, colour, alignment).                                           |
| Formatting | Bold, italic and colour on characters; bulleted and numbered lists on paragraphs; font, size, colour and alignment on the box.                                           |
| Undo       | A burst of typing is one step, with the height that follows it. A paste, a drop and composed text are steps of their own. Commands (bold, lists) are steps of their own. |
| Interface  | No change to `@galatsa/extension-api`; its version stays 1.4. The renderer's `beginTextEdit` and the editor gain what editing needs (below).                             |

### Layout in the browser

The renderer lays text out with the browser wherever there is a document (`DomTextEngine`, `text-dom.ts`), and with its own simple line breaking only where there is none (tests in Node, a worker later). The text is put into a hidden element at the reference size, a block per paragraph and a span per run, with every style that affects layout set explicitly (`all: initial` first, so page styles cannot reach it). Then:

- **Lines** are found by a binary search over the grapheme clusters of each paragraph: a line ends where the next cluster's box is half a line lower. A paragraph of n clusters on k lines takes about k·log n rectangles.
- **Baselines** come from an empty inline block at the start of each paragraph, whose bottom is the first line's baseline. Lines below follow at the line height when the paragraph is exactly as tall as its lines, otherwise at the clusters' own tops (a fallback font that made a line taller).
- **Fragments**: each run on a line is one fragment, from its first visible character to its last, with its left edge and width as the browser placed them. Spaces around it are not drawn.
- **List markers** are drawn by the canvas, right-aligned in the indent; the editing element shows the same marker with CSS (`::before`).

The canvas draws each fragment with `fillText` at its left edge, with the font from the size ladder of 0004 and the rest of the scale in the matrix. Glyph advances at the drawn size can differ from the layout's, so each fragment is stretched along its line to the width the layout gives it (`#fit` in `draw-context.ts`, remembered per fragment and font size). In Chromium the canvas also gets `textRendering = "geometricPrecision"`, which turns off hinted advances.

**Why 1,000 pixels.** 0004 said 100. Chromium lays text out with glyph advances rounded to whole pixels (on this machine, headless, Noto Sans: a line of 34 characters 1,529 pixels wide at 100 pixels where the font says 1,524.7, 0.3 % wider). The editing element shows those rounded advances scaled up, so zoomed in, its glyphs stood up to 4 pixels from where the canvas drew them. At 1,000 pixels the rounding is a tenth of that, and the measurements below show no difference left. Firefox lays text out with fractional advances and was fine either way.

**What was measured** (`tests/e2e/text-visual.spec.ts`, Chromium 158 and Firefox 159 headless, this machine, device pixel ratio 1): a box of 60 world units with bold, italic, coloured text, a bulleted list, ligatures and Norwegian letters, screenshotted as drawn and then with editing started. Pixels that differ by more than a quarter of the range from every pixel around them, as a share of the text's pixels; and how far the text's centre of mass moved:

| Zoom | Chromium, 100 px | Chromium, 1,000 px and unhinted canvas | Firefox, 1,000 px |
| ---- | ---------------- | -------------------------------------- | ----------------- |
| 0.1  | 1.3 %, 2.1 px    | 0 %, 0.7 px                            | 0.4 %, 0.2 px     |
| 1    | 3.9 %, 0.4 px    | 2.0 %, 1.0 px                          | 0.2 %, 0.4 px     |
| 8    | 1.8 %, 2.4 px    | 0 %, 0.0 px                            | 0 %, 0.0 px       |
| 40   | 0.3 %, 1.3 px    | 0 %, 0.0 px                            | 0 %, 0.0 px       |

At zoom 1 in Chromium the remaining differences are glyph by glyph, a pixel either way (checked word by word: every word starts at the same pixel or one off); the line ends agree to the pixel. The test requires under 5 % and under 1.5 pixels.

Rejected first: laying the text out with our own line breaking at 100 pixels (0004's first version, measured on the canvas) and giving the editing element the same breaks. The editing element would have to be forced to break where we say (a `<br>` per line, which the user could then edit), and the browser would still place glyphs its own way.

### Fonts

| Family         | Generic name | Styles                                           | Licence | Package (version)                    |
| -------------- | ------------ | ------------------------------------------------ | ------- | ------------------------------------ |
| Noto Sans      | `sans`       | regular, bold, italic, bold italic               | OFL-1.1 | `@fontsource/noto-sans` (5.3.0)      |
| Noto Serif     | `serif`      | regular, bold, italic, bold italic               | OFL-1.1 | `@fontsource/noto-serif` (5.3.0)     |
| Noto Sans Mono | `mono`       | regular, bold (italic is slanted by the browser) | OFL-1.1 | `@fontsource/noto-sans-mono` (5.3.0) |

Why these: one design family across sans, serif and monospace; real bold and italic faces (a synthesised bold or italic differs between browsers); Latin with Norwegian letters, Greek, Cyrillic and Vietnamese, so a presentation in another script still has the same font in every browser; quiet shapes that suit slides. The Fontsource packages split each face by script (`unicode-range`), so a page loads only the files its text needs, and they come from npm like every other dependency, are checked by the licence and release-age checks, and are served by the program itself: nothing is fetched from the internet. `@galatsa/renderer/fonts.css` brings them in; a page imports it once (the development page does).

**Licence.** The SIL Open Font License 1.1 is free; the FSF lists it as "a free copyleft license for fonts" in its section on font licences (https://www.gnu.org/licenses/license-list.html#SILOFL, read 2026-11-27). The fonts are data the program loads, not code combined with it, and the licence itself allows them to be "bundled, redistributed and/or sold with any software, provided that each copy contains the above copyright notice and this license" (Permission & Conditions, item 2, in the packages' `LICENSE` files). The licence check (`scripts/lib/licenses.ts`) accepted OFL-1.1 for development only, noting that shipped fonts needed their own decision; it now accepts it in production for the three font packages by name (`FONT_PACKAGES`), and for nothing else. **To do when the program is packaged:** each copy must carry the fonts' copyright notice and licence. Fontsource's files are cut from the Noto fonts, whose name tables normally hold both (assumed, not checked for these files); copying the packages' `LICENSE` files into the release is the safe way.

**Waiting for the fonts.** Before laying text out, the renderer asks the document's font set whether every font the text uses is ready for its characters (`document.fonts.check`). If not, it starts loading them, lays the text out with what there is, does not keep that layout, and draws again when the fonts have come (`FontWaiter`, `fonts.ts`). A font that loads nothing for the characters (no face covers them) is not waited for again. When the canvas is mounted, the renderer starts loading the Latin part of every bundled face, so the first text rarely waits.

### Data

This is part of the file format. Every key is optional when read; a missing key means its default, forever. New text boxes are written with every key.

| Key          | Value                                               | Default     |
| ------------ | --------------------------------------------------- | ----------- |
| `text`       | Shared rich text (`Y.Text`), attributes below       | empty       |
| `fontFamily` | A generic family name: `sans`, `serif`, `mono`      | `"sans"`    |
| `fontSize`   | Font size in world units, above 0, at most 2⁴⁶      | `24`        |
| `color`      | `"#rrggbb"` or `"#rrggbbaa"`, written in lower case | `"#1e293b"` |
| `align`      | `left`, `center` or `right`                         | `"left"`    |

Rich text attributes: `bold: true`, `italic: true` and `color` on characters; `list: "bullet"` or `"ordered"` on the `"\n"` that ends a paragraph (a paragraph's attributes live on its line break, as in Quill and most editors over Y.Text). Character attributes never go on a `"\n"`, and `list` only on one. New text ends with `"\n"`, so every paragraph has one to carry its list; text without it (older or foreign) is read the same, its last paragraph without a list, and the first list command or Enter at its end adds the line break. Numbering counts the numbered paragraphs that follow each other. The renderer reads these attributes for any element type that lays out rich text (`rich-text.ts`); unknown attributes are ignored.

**Growing the format.** A family name or an alignment of a later version is kept and read without a report, and drawn as sans serif or left, as 0005 section 3.2 allows; the commands write only what this version knows. The box height is the envelope's size; the text's height is derived and not stored.

A new text box's font size is 24 screen pixels at the zoom it is made at (rounded to three digits), and its width twelve font sizes. Its first line is centred on the click.

### Editing in place

`CanvasRenderer.beginTextEdit(id, options)` lays the editing element over the element's text area: the hidden layout element's structure and styles, made `contenteditable`, transformed by the element's matrix (rotation, the camera) and the reference scale, and placed again in every frame on screen, so it follows the camera and the element. While it is there, the canvas leaves that element's text out. It needs a mounted canvas; elsewhere (Node) it throws and the editor reports that the text cannot be edited.

The element never holds the text. It turns every edit into a replacement (`TextEdit`: so many characters at an index replaced by a text) and hands it to the editor, which writes it to the shared text and shows the result with `setContent`:

- **Typing, deleting, Enter, pasting, dropping, spelling corrections** come as `beforeinput` events, which are cancelled and turned into replacements (deletions by the browser's target ranges, or by grapheme, word or line from the caret). Pasting takes plain text (`text/plain`; rich paste is later work). Dropping into the text is refused.
- **Composition** (input methods, and dead keys on some systems) cannot be cancelled: the browser changes the element while the user composes, and nothing is written meanwhile. When composition ends, the element's text is compared with what was shown, and the difference goes on as one replacement. Changes by others that come during composition are held back and shown afterwards; the composed text is moved past them (`transformEdit`).
- **Undo and redo** (Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y, and the browser's own undo, `historyUndo`) run the document's undo, and the caret goes to where the change was.

The editor's side (`TextEditController`, `packages/editor/src/text-edit.ts`):

- Each edit is written in a transaction of the binding's origin, which the document's undo manager tracks, so typing joins the one history and a burst of typing is one step (0005 section 3.5). Inserted characters take the formatting of the character before them in their paragraph (at a paragraph's start, of the one after), never a paragraph's list; an inserted line break gives both halves the paragraph's list. Enter in an empty list item ends the list, and deleting the line break before a list item takes it out of the list instead of joining it to the paragraph before.
- With `autoHeight`, the box's height follows the text after each edit, in the same undo step.
- A paste, a drop and composed text are undo steps of their own (the undo manager stops capturing before and after them). Typing just before and after a paste would otherwise be one step with it, and an undo after composing would take back what was typed before.
- Keys: Escape ends editing. Keys with Ctrl, Cmd or Alt run undo and redo and the shortcuts of the edited type's own extension (bold, italic, lists); every other key is the element's (Ctrl+A selects the text, Ctrl+C copies it, the arrows move the caret). Keys and presses inside the element never reach the canvas: Space and Shift+1 are text, not the hand and "show everything" ([0009](0009-camera.md)).
- Starting: the text tool makes a box and starts editing it; Enter edits the one selected text box; a double click (two presses within 500 ms and 5 pixels) on a text box edits it with the caret where it was clicked, and the second press is not given to the tool.
- While its text is edited, the element is outlined (a dashed line) and not selected, so the selection tool's handles do not stand on the text. When editing ends the element is selected.
- Ending: Escape, a press on the canvas, the element going away (an undo, someone else deleting it), the input being turned off, the editor closing. A text box left empty is removed: when the press that started editing made it (the text tool) and nothing was typed, its creation is taken back as if it never happened (no undo step, no redo step); otherwise it is deleted as an undo step.
- A pinch that turns out to have begun with the text tool's press takes back the box, as 0009 describes; editing ends with it, and nothing typed is lost because nothing could be typed yet.

The editor's text service (`services.text`) now reports the edited element, its data key and the selection, and moves the selection, as 0005 section 4.8 describes.

### Commands and fields

| Command              | Shortcut                     | Does                                                                                                                                               |
| -------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `insert`             |                              | Makes a text box (position, width, text and style optional).                                                                                       |
| `set-style`          |                              | The fields' command: font, size, colour or alignment of the given boxes. A change that changes nothing is not offered.                             |
| `bold`, `italic`     | `Mod+B`, `Mod+I`             | While editing: the selection, or the word at the caret. Otherwise: the whole text of the selected boxes. Off when all of it has it already.        |
| `bullets`, `numbers` | `Mod+Shift+8`, `Mod+Shift+7` | While editing: the paragraphs the selection touches. Otherwise: every paragraph of the selected boxes. Off when all of them are already that list. |

Fields (all offered in quick mode): size, colour, alignment and font. The properties panel that shows them is F1-16.

- `scripts/lib/licenses.ts`: OFL-1.1 accepted in production for the three font packages.
- `tests/e2e/playwright.config.ts`: the text tests in the Firefox and WebKit projects.

## Known limitations

- **Right-to-left and mixed-direction text** are laid out by the browser but drawn left to right: a fragment is drawn from its left edge as one string, which is wrong for a right-to-left run. Not handled yet.
- **Rich paste**: pasting takes plain text; formatting from another program is dropped.
- **Height outside editing**: the height follows the text while it is edited. When a box's width or font size changes without editing (a resize, the size field), the text is laid out again at the new width, but the box keeps its height until the next edit, so the text may stand out below the box or leave space. A hook on the type (a size the box takes for a width) used by the resize and scale commands would fix it; that touches the basics and the interface and was left out.
- **Formatting at a collapsed caret** formats the word at the caret; there is no "bold from here on" for the next typed characters.
- **Very small text** (a few pixels on screen) is drawn by the canvas with each fragment stretched to the browser's width; individual glyphs can stand a pixel apart from where the editing element puts them. Text under 4 device pixels is drawn as bars by the canvas and as tiny text by the editing element.
- **Editing at extreme zoom**: the editing element is as large as the text on screen; at a zoom where one glyph is thousands of pixels the browser has to raster a very large element. Tested up to zoom 40 with 60-unit text (2,400-pixel glyphs).
- **Lines made taller by a fallback font** (a character no bundled font has) are placed by the clusters' tops, which are the fallback font's content area; the baseline there may be off by a pixel or two.
- **Layout costs a reflow**: each new layout builds the hidden element and reads rectangles; layouts are cached (0004). Measured in the benchmark run: see Tests.
- **Spell checking** is off in the editing element: the element is rebuilt after each edit, which would make the browser's marks flicker.
- **Tab** inserts nothing (it would move the focus out of the text). Lists have one level.
- **Upgrading the layout before typing** (0005 section 3.8) is not done by the binding: version 1 is the only layout. A later layout must upgrade before the first keystroke.
- **Input methods** are tested with Chromium's DevTools protocol (`Input.imeSetComposition`) in Chromium; in Firefox and WebKit the test sends the composition events and changes the element as a browser does, which tests the program's handling but not the browser's. Real input-method windows were not tested.
- **WebKit**: Playwright's WebKit cannot run on the development machine; the tests run in WebKit in CI only. Not checked in the system's WebKitGTK yet.
- The text sketch (`examples.text`) stays in the examples as it was; the development page no longer loads it.
